# Промпты для реализации: медиа-коллаж и Rueckblick

Источник ТЗ: `docs/features/media-collage-rueckblick.md`

Этот файл разбивает ТЗ на этапы и атомарные промпты для отдельных AI-сессий. Промпты рассчитаны на последовательный запуск: каждая новая сессия должна сначала получить общий префикс, затем один конкретный атомарный промпт.

## Как использовать

1. Запускай промпты по порядку.
2. В новую AI-сессию копируй блок **"Общий префикс для каждой сессии"** и один промпт из нужного этапа.
3. Если предыдущий этап уже частично реализован, AI должен сначала проверить текущее состояние файлов и продолжить без дублирования.
4. Каждый промпт ограничен своим scope. Не проси одну сессию делать следующий этап "заодно".
5. После каждого этапа желательно сохранять изменения отдельным коммитом или хотя бы проверять `git diff`.

## Общий префикс для каждой сессии

```text
Ты работаешь в проекте `berufsorientierung_app`: SvelteKit 2, Svelte 5, TypeScript, Cloudflare D1/R2, Vitest. Главный источник требований: `docs/features/media-collage-rueckblick.md`.

Перед изменениями:
- выполни `git status --short`;
- прочитай `docs/features/media-collage-rueckblick.md`;
- прочитай только те файлы, которые нужны для текущего атомарного промпта;
- сохрани существующие паттерны проекта, стиль Svelte-компонентов, DB-модулей, i18n и проверок.

Правила:
- реализуй только текущий атомарный промпт;
- не реализуй будущую админку медиа, если промпт явно не из раздела "Будущий этап: админка";
- не меняй unrelated-файлы и не откатывай чужие изменения;
- публичные медиа показывай только если соответствующий флаг публикации равен `1` и `status != 'hidden'`;
- видео не должно autoplay, preload полной загрузки и запускаться без клика пользователя;
- все query-параметры публичных страниц валидируй и приводи к безопасным значениям;
- ошибки БД/R2 логируй на сервере и не роняй публичные страницы;
- после изменений запусти минимально релевантные проверки, обычно `npm run check`; для финальных или UI-этапов также `npm run build`; для DB-логики добавь/запусти релевантные Vitest-тесты.

В финальном ответе:
- перечисли измененные файлы;
- кратко объясни, что реализовано;
- укажи, какие проверки запускались и их результат;
- если что-то не удалось проверить, явно напиши почему.
```

### Промпт 02: добавить типы и DB read-модуль для медиа

```text
Используй общий префикс.

Задача: добавить типы и read-only DB-модуль для публичной работы с `event_media` и `media_settings`.

- `EventMediaType = 'image' | 'video'`;
- `EventMediaStatus = 'uploaded' | 'hidden'`;
- `EventMedia`;
- `PublicEventMedia`;
- `MediaSettings`;
- `RueckblickMediaFilters`;
- дополнительные small-типы допустимы, если они упрощают сигнатуры.

DB-функции:
- `getMediaSettings(db)`;
- `getHomepageMedia(db, limit?)`;
- `getRueckblickMedia(db, filters)`;
- `getRueckblickEvents(db)`;
- `getEventMediaObjectKeys(db, eventId)`.

Требования к `getMediaSettings`:
- читать строку `id = 1`;
- если строки нет, возвращать безопасные дефолты 300 фото и 30 видео;
- не падать из-за отсутствия optional-полей.

Требования к `getHomepageMedia`:
- возвращать только `show_on_homepage = 1` и `status != 'hidden'`;
- применять ограничения из ТЗ: фото до 3 MB, видео до 30 MB и до 10 секунд;
- учитывать лимиты из `media_settings`: по умолчанию максимум 300 фото и 30 видео;
- сортировать выбранные медиа по `created_at DESC`;
- не возвращать больше лимитов, даже если в БД опубликовано больше;
- если есть параметр `limit`, он может дополнительно ограничивать итоговый список, но не должен обходить лимиты настроек.

Требования к `getRueckblickMedia`:
- возвращать только `show_on_rueckblick = 1` и `status != 'hidden'`;
- поддерживать фильтры `eventId`, `dateFrom`, `dateTo`, `sort`, `page`, `pageSize`;
- при выбранном `eventId` не включать `media_scope = 'general'`;
- дата сортировки и фильтрации: `COALESCE(event_media.captured_at, events.date, event_media.created_at)`;
- поддерживать `newest` и `oldest`;
- использовать limit/offset или другой простой pagination-подход;
- не собирать SQL через небезопасную конкатенацию пользовательских значений.

Требования к `getRueckblickEvents`:
- вернуть список мероприятий, у которых есть хотя бы одно публичное Rueckblick-медиа;
- не включать general media как отдельное мероприятие;
- сортировать варианты удобно для фильтра, например по дате события DESC.

Требования к `getEventMediaObjectKeys`:
- вернуть `object_key` и `thumbnail_object_key` для всех media конкретного мероприятия;
- функция понадобится для удаления R2-объектов при hard-delete мероприятия.

Не делать:
- не добавлять create/update/delete медиа;
- не реализовывать upload;
- не менять публичные страницы;
- не менять админку.

Проверки:
- запусти `npm run check`;
- если в проекте есть подходящий паттерн unit-тестов DB-модулей, добавь минимальные тесты здесь или оставь их для следующего промпта 03.
```

```text

- читать query-параметры `eventId`, `dateFrom`, `dateTo`, `sort`, `page`;
- валидировать параметры и заменять невалидные безопасными значениями;
- `sort` поддерживает `newest` и `oldest`, дефолт `newest`;
- `page` минимум 1;
- использовать ограниченную загрузку, например `pageSize = 24` или близкое значение;
- загрузить media через `getRueckblickMedia(db, filters)`;
- загрузить список мероприятий для фильтра через `getRueckblickEvents(db)`;
- возвращать media, events/filter options, текущие фильтры и pagination-данные;
- если БД недоступна или запрос упал, залогировать ошибку и вернуть безопасные пустые данные.

- страница должна получать только медиа с `show_on_rueckblick = 1` и `status != 'hidden'`;
```
